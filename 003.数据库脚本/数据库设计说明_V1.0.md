# 医疗智能体管理平台数据库设计说明 V1.0

## 1. 设计范围

本版本覆盖以下模块：

1. 用户登录功能（注册、密码/短信登录、失败锁定、验证码、会话、登录审计、密码重置基础能力）
2. 用户中心（组织、用户、角色、功能权限、数据权限、医院员工同步）
3. 智能体接入中心（注册申请、修订、模型配置、备案材料、接入密钥、连通测试、审核、状态轨迹）
4. 智能体统一台账中心（统一智能体主数据、生命周期、风险分级、版本、材料、资源与评测引用、指标快照）

建表脚本：[医疗智能体管理平台_表结构_V1.0.sql](./医疗智能体管理平台_表结构_V1.0.sql)

已建库备注修复脚本：[医疗智能体管理平台_表和字段备注修复_V1.0.1.sql](./医疗智能体管理平台_表和字段备注修复_V1.0.1.sql)

备注中文化脚本：[医疗智能体管理平台_备注中文化修复_V1.0.2.sql](./医疗智能体管理平台_备注中文化修复_V1.0.2.sql)

## 2. 设计依据

- 《医疗智能体管理平台-需求说明书V1.2.4.md》：注册与登录规则
- 《用户中心-需求说明V1.4.md》：用户、角色、功能权限与数据范围
- 《智能体接入中心-需求说明书V2.1.md》：接入申请、连通测试、审核和台账同步
- 《统一台账中心-需求说明文档V1.8.md》：台账列表、画像、生命周期和风险分级
- 当前前端 `src/pages`、`src/types`、`src/mock`：多角色、医院员工同步、组织/用户数据权限覆盖、多模型配置及台账展示字段

## 3. 关键设计决定

- 使用 MySQL 9.x 可执行、同时保持 MySQL 8.0.19+ 兼容的基础 DDL；字符集为 `utf8mb4`，排序规则为 `utf8mb4_0900_ai_ci`。
- 所有业务主键采用 `BIGINT UNSIGNED AUTO_INCREMENT`；对外暴露业务编号，不向前端暴露自增主键。
- 用户密码、短信验证码、访问令牌只保存不可逆摘要；智能体 API Key/平台密钥只保存应用层加密后的密文及末四位。脚本不包含任何明文默认密码。
- 接入申请采用“申请单 + 不可变修订版本”模型，审核绑定具体修订版本，避免申请人修改后破坏历史审核证据。
- `agt_agent` 是智能体统一主数据；`led_agent_ledger` 仅保存台账管理状态，不重复保存名称、科室、供应商等接入基础信息。
- 接入审核通过后，应在同一事务内更新 `agt_agent`、创建/更新 `led_agent_ledger`，并写入 `integration_outbox_event`，由异步消费者通知评测、审计和通知模块。
- 数据权限采用“策略 + 角色/组织/用户绑定 + 指定科室/智能体/数据分级明细”，支持组织默认和用户级覆盖。
- 门户 PRD 要求自助注册后分配“普通用户”，而用户中心 V1.4 重点描述三类管理角色；初始化数据保留四个系统角色，以同时满足两个入口。

## 4. 表分组

本版共创建 43 张表，分组如下：

| 分组 | 表 |
| --- | --- |
| 基础与文件 | `sys_schema_version`、`sys_department`、`sys_file_object` |
| 登录与用户 | `iam_user`、`iam_user_password`、`iam_sms_verification_code`、`iam_login_session`、`iam_login_log` |
| 角色与功能权限 | `iam_role`、`iam_user_role`、`iam_permission`、`iam_role_permission` |
| 员工同步 | `iam_hr_sync_batch`、`iam_hr_sync_item` |
| 智能体接入 | `agt_agent`、`agt_agent_clinical_stage`、`agt_registration_application`、`agt_registration_revision`、`agt_registration_model`、`agt_registration_file`、`agt_access_config`、`agt_connection_test`、`agt_registration_review`、`agt_registration_status_history`、`agt_agent_document` |
| 数据权限 | `iam_data_policy`、三个策略绑定表、三个策略范围明细表 |
| 统一台账 | `led_agent_ledger`、`led_agent_version`、`led_lifecycle_event`、`led_risk_question`、`led_risk_option`、`led_risk_assessment`、`led_risk_answer`、`led_resource_link`、`led_evaluation_ref`、`led_metric_snapshot` |
| 模块联动 | `integration_outbox_event` |

## 5. 执行方式

```bash
mysql --default-character-set=utf8mb4 -u <用户名> -p < 医疗智能体管理平台_表结构_V1.0.sql
```

已有 V1.0 数据库只需执行备注修复脚本：

```bash
mysql --default-character-set=utf8mb4 -u <用户名> -p < 医疗智能体管理平台_表和字段备注修复_V1.0.1.sql
```

脚本仅执行 `CREATE DATABASE/TABLE IF NOT EXISTS` 和基础字典初始化，不包含 `DROP`、清库或覆盖业务数据操作。生产执行前请由 DBA 将数据库名、存储路径、备份策略、KMS 密钥管理和账号最小权限调整为医院规范。

## 6. 事务与并发要求

- 生成“科室编号-四位顺序号”时必须通过事务和唯一索引兜底，禁止用“当前条数 + 1”。
- 申请状态更新必须带 `row_version` 做乐观锁，并同步追加状态历史。
- 每个智能体只能有一条 `is_current=TRUE` 的风险评定；生成列唯一索引负责数据库兜底，切换当前版本仍应在一个事务内完成。
- 密钥解密、登录日志查看、批量导出等敏感操作应在应用层二次鉴权并写审计事件。
- `led_metric_snapshot` 是运行监控数据的查询快照，不是监控明细事实表；监控明细应由运行监控模块独立存储。
